# Client professional search architecture

- **Production file:** `public/js/client-dashboard/client-professional-search.js`.
- **Purpose:** Lets a client search professionals by name above the bookings sidebar, lock one professional's public schedule onto the client's own calendar to find an open slot, unlock it, and favorite/unfavorite professionals into a short persistent list. Only one professional's schedule is ever locked/visible at a time. The locked professional always appears as a small chip/bubble in the same row as favorited professionals (with a lock icon and an active color state) rather than a separate banner; an unfavorited locked professional gets a temporary bubble that disappears once unlocked. Favoriting is a heart-shaped toggle (empty outline when not favorited, filled and colored red when favorited, using a standard symmetric heart glyph at 14px for crisp rendering) fully independent of the lock state, so favoriting/unfavoriting never locks, unlocks, or reorders the currently-locked chip. Hovering over a professional's name — in the search results before any action, or in the favorited/locked row afterward — shows their profile identifier (`idTag`, falling back to the raw document ID) via a native tooltip, so a client can distinguish two similarly-named professionals.
- **Imports:** `findPublicProfiles` from `search/search-professional.js`, `debounce`/`escapeHtml`/`normalizeSearchTerm` from `core/utils.js`, `UI_STRINGS.clientDashboard.professionalSearch`.
- **DOM owner:** Owns the `data-client-professional-search` region in `client-dashboard.html`, inserted above `[data-client-bookings-root]`; driven by `client-dashboard.js` the same way `client-bookings.js` and `client-schedule.js` are (re-invoked on every state change, no internal persistent state of its own).
- **Firestore/Storage:** No direct reads/writes; `client-dashboard.js` supplies `savedProfessionals` and the locked professional's `busySlots`, and performs the `publicProfiles`/`busySlots` reads and the `clientAccounts` write.
- **Security rules:** No `firestore.rules` change required; reuses `allow read: if true` on `publicProfiles`/`busySlots` and the existing `allow read, create, update: if isOwner(clientId)` on `clientAccounts`.
- **Feature flag:** None; reuses the existing authenticated client-dashboard gate.
- **Mockup references:** `docs/requirements/MASTER_SPECIFICATION.md` Part 7 (client dashboard) and Part 11 (Phase 9b).
- **Verification:** Phase 9b entry in `docs/verification/VERIFICATION_LOG.md`; AI authenticated browser smoke test passed with three seeded professionals (search with id tooltip, lock/overlay, unlock, heart favorite/unfavorite toggle independent of lock state, switching lock between all three with no cross-professional overlay leakage, reload persistence for all three favorites).
